# Tasks: Transaction audit log

**Input**: Design documents from `/specs/002-transaction-audit/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Tests**: REQUIRED for every behaviour change and every RLS policy (Constitution III and V). Within a phase, write the tests first and confirm they fail before implementing. Every row 28–42 of [access-matrix.md](contracts/access-matrix.md) has its own pgTAP task with an allowed and a refused case.

**Organization**: Phases follow the **four delivery slices in plan.md**, not story priority order. Each slice is one PR that leaves `main` green. Slice 1 = Phases 2–3 (US1), slice 2 = Phase 4 (US4), slice 3 = Phase 5 (US2), slice 4 = Phase 6 (US3). Migration B is a separate later PR (Phase 4b).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: the user story from spec.md (US1–US4). Setup, Foundational and Polish tasks have none.
- **🧑 manual**: Sam does it (production check). An agent prepares the query but must not run it against production.

## Conventions

- Create each migration with `npx supabase migration new <name>`; the file lands in `supabase/migrations/<ts>_<name>.sql`. Keep the order A1 → A2 → A3 → A4 → reads → B.
- New pgTAP files go in `supabase/tests/`, start with the comment convention used by `row22_admin_set_allowance.sql`, run in a rolled-back transaction, and use the `tests.*` helpers from `00_helpers.sql`. Never `delete from audit_log` in a test (immutable); use rollback.
- Every `private` function: `security definer`, `set search_path = ''`, `revoke all … from public, anon, authenticated, service_role` by name (ADR 0009). Exception: `private.can_view_audit` keeps `execute` for `authenticated`.
- `audit_log` before/after values come from an explicit field list per table, never `to_jsonb(row)` (FR-007).
- Audit reads always use the user's session, never the secret key.

## Decisions made while writing these tasks

1. **Slices 1 and 2 stay separate PRs.** Slice 1 is two migrations plus about 20 pgTAP files; slice 2 is a backfill, an RPC swap, three page edits and edits to four existing tests. Together that is too large for one review. Sam can merge them if preferred; if so, the cutoff rule in A038 becomes unnecessary.
2. **Backfill moves to slice 2.** plan.md's slice 1 line says "A1–A3" but its slice 2 line says "A4 backfill". The backfill (A3) is US4 and is built in slice 2 (Phase 4). Slice 1 = A1 + A2 only.
3. **Backfill cutoff.** Between slice 1 and slice 2 shipping, live triggers write entries (and allowances are double-written, plan.md slice 1). A plain backfill would duplicate them. A038 therefore only backfills source rows older than the first live entry (`min(created_at)` over `is_backfilled = false`), and A034 tests it. This refines R7.
4. **My history sits in the main nav**, as "History" (Lucide `History` icon) between Calendar and Profile, for all roles. DIRECTION.md defines only the sidebar and mobile bottom bar, not a placement. Admins would then have 7 bottom-bar items, so A060 checks it at 360 px and, if it does not fit, falls back to a link on the Profile page. The Audit page is a tab in `AdminTabs`, not a main nav item.
5. **Read functions split by slice.** plan.md has one `audit_reads` migration (A5). To let slice 3 ship alone it becomes two files: `audit_my_history` (slice 3) and `audit_search` + `audit_export_csv` (slice 4).
6. **Shared filter.** `audit_search` and `audit_export_csv` share one `security invoker` helper, `private.audit_matches(...)`, so screen and file cannot drift (database-api.md). Authenticated already has `usage` on `private` for the existing policies.
7. **A test task that lands before its implementation guards its assertions.** A034–A037 assert behaviour that A038–A040 add, and one task is one PR, so an unguarded file would put a red check on `main`. Each guards on whether its subject exists — A034 on `to_regprocedure('private.audit_backfill()')`, the existence check `00_helpers.sql:151` already uses for `tests.audit_entries` and the form A007 asked for. The guard is deleted in the PR that lands the behaviour, and the test PR's body carries the local red-then-green run taken with it out. Where an assertion is already true on `main` (A035 and A036: slice 1's triggers write the entries) the guard wraps only the half that is not, and A007 shows the third case — a `proname like 'audit%'` sweep needs no guard at all, because it covers nothing until the function exists.
8. **An `allowance_changes` row with `new_days` null backfills as `allowance_removed`, not `allowance_set`.** That row *was* a removal, and the live trigger for one writes `allowance_removed` with the `days` key present and null plus `context.default_days`. The backfill matches the live shape so the three allowance panels read one vocabulary; the alternative would need a special case in every reader.
9. **R7's `on conflict (source_key)` needs the index predicate.** `source_key` is unique through a *partial* index (`20261116062027_audit_log.sql:45`), and Postgres infers an `ON CONFLICT` arbiter against a partial index only when the predicate is repeated, so A038 writes `on conflict (source_key) where source_key is not null do nothing`. A bare `on conflict (source_key)` fails with `42P10`.
10. **A045's equality only holds if slices 1 and 2 reach production in one `db push`.** If slice 1 deploys first, the rows written in between are newer than decision 3's cutoff and correctly stay un-backfilled, so `old_rows > backfilled` on a healthy database and the `reason` text of exactly those rows is the one thing `allowance_changes` still holds. Unresolved when written, and Sam's to decide — see #366. *What was predicted is what happened: production took slice 1 at 01:15:44Z and the A039 swap at 12:34:29Z on 2026-11-17 (both read out of the **Deploy DB** job logs, run 43994137554 and run 44084218732), so the two numbers differ by the allowance changes made inside those eleven hours — and by nothing else, because the swap is the minute `allowance_changes` stopped gaining rows. [quickstart step 4](quickstart.md) carries the three-number query that separates that expected gap from a carry-over that silently skipped a row.* **Settled by A045 on 2026-11-17, and the gap is zero: production reads `old_rows = 0`, so those eleven hours contain no allowance changes at all and `old_rows - backfilled = 0`. The consequence this decision was written to guard against is therefore discharged rather than decided — the rows whose `reason` text only `allowance_changes` held do not exist, so migration B destroys nothing. What the reading cannot do is validate the `ac:` branch of the carry-over, because production has never given it a row to carry. That branch is proven against a fresh install and nowhere else, and A046 should be reviewed with that limit stated rather than assumed away.**
11. **The backfill inserts into `audit_log` itself; it cannot call `private.audit_write`.** `audit_write` takes its actor from `private.audit_actor()`, which reads `auth.uid()` — and a migration runs as the owner with no JWT, so every backfilled entry would record `System` with a null actor id instead of the person who actually submitted or decided. A038 therefore names the actor columns from the source row and looks up the current `full_name`, `role` and `is_demo` from `profiles`, duplicating the two derivations `audit_write` does. A034's actor and `is_demo` assertions are what keep the duplication honest.
